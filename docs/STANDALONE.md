# Ariadne standalone (Docker Compose on a single machine)

The open source distribution of Ariadne is the [`docker-compose.yml`](../docker-compose.yml) at the repository root. It
brings up the whole stack on one machine, CPU-only and without AVX (ARCHITECTURE.md, section 9). Third-party images are
public and pinned; Ariadne's own images are built from this repository (or pulled from a public registry, via a variable).

## Getting started

```bash
deploy/standalone/init-env.sh          # .env from .env.example, with secrets generated by openssl rand
deploy/kiwix/get-test-zim.sh           # a 1.8 MB ZIM in ./data/zim (Kiwix needs at least one; add real libraries later)
docker compose up -d --build           # the profiles in COMPOSE_PROFILES (set to "all" in .env)
docker compose logs bootstrap          # the app's admin key (it only appears here)
curl localhost:8800/health             # "status":"ok"; services you did not switch on say "not configured"
```

The first run is slow: **18 minutes were measured with a warm build cache**, more on a cold machine. It compiles kiwix-serve with its skin and llama.cpp, installs Moodle (a few minutes; on an Apple
Silicon Mac, Jobe runs emulated as amd64) and downloads the models (the embedder, ~470 MB; the curator, ~2.5 GB;
LibreTranslate en+pt; the Wiki.js locales). After that, `docker compose up -d` is idempotent and the `bootstrap*` services
only do what is still missing.

Prebuilt images are not published yet: build them with `docker compose up -d --build`. If you keep the images in a registry of
your own, set `ARIADNE_IMAGE_PREFIX=<registry>/<owner>/ariadne-` and `ARIADNE_TAG=<version>` in `.env`, then run `docker compose pull`
and `docker compose up -d` (without `--build`). The images are `ariadne-server`, `-kiwix`, `-moodle`, `-calibre`, `-jobe` and `-curator`.

### Profiles

The core always starts: `postgres`, `kiwix`, `server`, `worker`, `worker-llm` (curation, kept separate because a rewrite
on CPU takes minutes and a worker runs one job at a time), `worker-heavy`, and the one-shot steps `init` and `bootstrap`.
Everything else is chosen with `COMPOSE_PROFILES` (in `.env`) or with `--profile`:

| Profile | Services | URL to leave empty without the profile |
|---|---|---|
| `wiki` | `wikijs` (tier 2), `bootstrap-wiki`, `wikijs-public` (the port) | `WIKIJS_URL=` |
| `books` | `calibre`, `kavita`, `bootstrap-books`, `kavita-public` (the port) | `CALIBRE_URL=`, `KAVITA_URL=` |
| `courses` | `moodle`, `jobe`, `jobe-gateway`, `bootstrap-courses` | `MOODLE_URL=`, `JOBE_URL=` |
| `translate` | `libretranslate` | `LIBRETRANSLATE_URL=` |
| `llm` | `curator` (llama-server on CPU) | `CURATOR_URL=` |
| `tunel` (not part of `all`) | `gpu-gateway` (tunnel for the GPU batch; needs your own Cloudflare tunnel) | – |
| `all` | everything above except `tunel` | – |

By default the server points at the compose services (`http://wikijs:3000`, …). With a profile switched off, leave its URL
empty in `.env` and Ariadne treats the service as "not configured" (`/health` stays `ok`). Alternatively, point the URL at
a service that already runs on another machine.

### What the `bootstrap*` services do on their own

`ariadne bootstrap` (`server/ariadne/cli_bootstrap.py`) runs as one service per profile, so a failure in one does not
delay the others. It uses the secrets from `.env` (none come from the code) and acts only when something is missing:

| Step | Where |
|---|---|
| Databases `ariadne`, `wikijs`, `moodle` | `deploy/postgres/init`, on first initialization |
| Migrations | the `server`, at startup |
| Wiki.js setup, API enabled, key | `bootstrap-wiki` (key → vault) |
| Locales and namespacing | `bootstrap-wiki`: the 69 locales Wiki.js routes (or `WIKIJS_LOCALES`), one at a time, each confirmed (`isInstalled`); only what actually installed goes into `namespaces`. Needs internet on the first run; the catalog cuts off bursts (429), so there are waits, and whatever is missing is left for the next run |
| Wiki.js theme (CSS, head, body, dark mode, logo) | `bootstrap-wiki`, only if the Wiki.js CSS is empty; fonts come from this installation's kiwix (`KIWIX_PUBLIC_URL`) |
| Moodle token | `bootstrap-courses` (waits for the install, token → vault) |
| Kavita administrator, library and key | `bootstrap-books` (key and id → vault) |
| Limited Postgres role for `gpu-gateway` | `bootstrap`, with `deploy/postgres/gpu-gateway.sql` (`GPU_GATEWAY_DB_PASSWORD`) |
| First app administrator key | `bootstrap` (if there is none; the key only appears in the log) |
| Owner of the data folders (uid 1000) | `init` (top-level folder only, and only if it is not owned by 1000) |
| Secrets | `deploy/standalone/init-env.sh` (`init` refuses to start while any value is `change-me`) |

Tokens go into the vault (`ARIADNE_MASTER_KEY`), which the server and workers re-read every ~5 s, so you do not need to
touch `.env` or restart anything. Without a master key, `bootstrap` prints the value so you can put it in `.env`.

## Security

- **Secrets.** `.env.example` only contains `change-me`. `init-env.sh` generates real values (`openssl rand`) into a `.env`
  with mode 600 and never prints them. `init` is the first service and refuses to start while any value is still
  `change-me`; Postgres and every service that holds secrets wait for it, so nothing is ever initialized with a placeholder.
- **Ports.** Only the human-facing ports and the app's own are published: `server` (8800), `kiwix` (8801), Wiki.js (8802),
  Moodle (8805) and Kavita (8806), and only on loopback: they open on `PUBLISH_ADDRESS`, which `init-env.sh` fills with the
  resolved `localhost` (Docker does not accept the name) and which has no default (without it Compose refuses to start).
  They do not answer from other machines: for that, put an HTTPS proxy in front (below). Postgres, Calibre, the Jobe
  gateway, LibreTranslate and the curator stay on the internal network. For tests and maintenance there is
  `deploy/standalone/ports.yml`, on the same `PUBLISH_ADDRESS`.
- **Wiki.js and Kavita open only once they are locked down.** A fresh Wiki.js accepts the setup of whoever arrives first,
  and the first registration on a fresh Kavita becomes administrator. Their published ports belong to a TCP proxy
  (`wikijs-public`, `kavita-public`) that only starts after `bootstrap-wiki` / `bootstrap-books` has done the setup and
  created the administrator.
- **Jobe.** Student code runs on an `internal` network (no outbound access) and Jobe is reachable only through the gateway,
  with a key and a rate limit. Moodle blocks every private network except the gateway's address, which it resolves by name
  on each request (Docker picks the subnet); if the name does not resolve, nothing gets through. No container with a
  published port sits on two networks (Docker Desktop lost port forwarding on those).
- **Private text.** It only goes to the compose services and localhost (`PRIVATE_ALLOWED_HOSTS`); a service outside that
  set has to be added to the list on purpose.
- **GPU batch.** Without the `tunel` profile nothing is reachable from the internet. With it, the gateway exposes only the
  four routes of a run, connects to the database with a role that can see only `batch_run`, and `cloudflared` exists only
  while a run is in progress.

## Exposing it beyond this machine

The ports stay on loopback on purpose: the app and MCP require a key, but kiwix, Wiki.js, Moodle and Kavita are meant for
people and travel over plain HTTP. To open them to a network or the internet, put an HTTPS proxy on the same machine
(Caddy, nginx, Traefik or a tunnel such as Cloudflare's) forwarding to `localhost:<port>`, and tell Ariadne the public
names:

```bash
# in .env, the names as the browser sees them (they go into responses and links)
KIWIX_PUBLIC_URL=https://kiwix.example.org
WIKIJS_PUBLIC_URL=https://wiki.example.org
```

With Caddy, for example, each name is a block `wiki.example.org { reverse_proxy localhost:8802 }` (the certificate is
automatic). Do not change `PUBLISH_ADDRESS` to a network address: traffic would stop being encrypted.

## Notes

- **Data folders.** `ZIM_DIR`, `BOOKS_DIR`, `COURSES_DIR` and `BACKUP_DIR` are host folders (`./data/…` by default),
  because they belong to the user (put your ZIM files there, take your backups from there). Service state lives in named
  volumes (`pgdata`, `models`, `moodledata`, `kavita-config`, `jobe-home`, `libretranslate-models`, `curator-models`).
- **No AVX.** kiwix-serve is built with `-O2` (never `-march=native`), llama.cpp with the flags from section 9.3 (the build
  fails if any unit comes out with AVX/FMA/F16C/BMI2), and the embedder is the ONNX model that passed the canary.
- **Two copies on one machine.** Use a separate compose project (`docker compose -p <name>`) and different ports in `.env`.
  Local builds are tagged `ariadne-server:local`, `ariadne-kiwix:local`, … regardless of the project, so a second copy that is
  built from other code overwrites them (and `docker compose down --rmi local` in one copy deletes the other's images). To keep
  copies apart, give each its own tag in `.env`: `ARIADNE_TAG=copy2`.
